# 初期版の設計・実装計画

## 目的と判断基準

`deordinal` は、文章、コードコメント、Python の docstring の冒頭にある順序ラベルを検出する Rust 製 CLI とする。順序に意味があるかどうかは初期版では判定しない。必要な順序は Markdown の明示的な ignore で許可する。

Pi 拡張の実装・テストは参考資料であり、互換性の要件ではない。個別の正規表現を増やすことより、検査対象の抽出、ルール、抑制、診断を分離し、各ルールの適用範囲と例外をテストで説明できることを優先する。`docs/vale.md` の方針どおり、Vale は基盤にしない。

初期版は検査のみを行う。`--fix` や `--unsafe-fix`、意味判定、JSON 出力、設定ファイル、Markdown 内の別言語の検査は実装しない。

## 対象

- Markdown: `.md`。見出し、本文、箇条書き、番号付きリスト、引用内の文章を検査する。コードフェンス、インラインコード、frontmatter、表、HTML 本文は検査しない。Markdown 中の JS/Python コードも検査しない。
- JavaScript: `.js`、`.jsx`、`.mjs`、`.cjs`。TypeScript: `.ts`、`.tsx`、`.mts`、`.cts`。Python: `.py`、`.pyi`。行頭・行末の行コメント、ブロックコメント、JSDoc など、各言語の構文木がコメントと判定する箇所を検査する。コードや通常の文字列リテラルは検査しない。
- Python の docstring は、モジュール、クラス、関数、非同期関数の本体の最初の文にある文字列リテラルとして識別し、内容の各行の冒頭を検査する。通常の文字列、単に複数行であるだけの文字列は対象外とする。`.pyi` にも同じ判定を適用する。
- `.mdx` は初期版では含めない。Markdown パーサーに拡張子を追加するだけでは JSX・式を Markdown 本文と誤認し得る。適切な MDX パーサーまたは検査対象範囲の明示が必要になった時点で検討する。

## 判定ルール

検査対象ごとに、文頭の構造的な記法を除去した文章と、元ソース中の位置を抽出する。例えば Markdown の見出し記号・引用記号・箇条書き記号、コメントの `//`・`#`・`/*`・JSDoc の `*`、Python docstring の引用符を区別して扱う。ファイル全体を行単位の正規表現だけで検査しない。

初期のルール群は以下を想定する。各ルールには安定した ID、対象コンテキスト、検出例・非検出例のテストを持たせる。

- `deordinal/ordered-list`: Markdown の番号付きリスト。リストを一つの構造として扱い、リストごとに診断する。入れ子のリストは別の構造として扱う。
- `deordinal/ordinal-prefix`: 文章冒頭の `1. 概要`、`1: 概要`、`A) 概要`、`(1) 概要`、丸数字などのラベル。階層番号、漢数字、単位・年・バージョンとの衝突は、ルール固有の肯定・否定テストを作りながら適用範囲を決める。半角コロンも対象にする。
- `deordinal/keyword-prefix`: `Step 1`、`Phase A`、`ステップ 1` などの先頭ラベル。見出しがラベルだけで終わる場合も検出する。対象語は独立した一覧で管理する。

同じ箇所を複数のルールが検出しないよう、Markdown の番号付きリストの構文と、文章中のラベルの適用範囲を分ける。数値から始まるだけの表現を無条件には違反としない。例えば `1.29 GB` や `2025 年` は否定例にする。文中に現れる参照表現は初期版では対象外とする。装飾がラベル自体を分断する Markdown（例: `**1.** 概要`）は、正しい位置を得られる方法を確認するまで対象外とし、境界例としてテストに残す。

判定を巨大な共通正規表現に集約しない。共通化するのは入力と診断の型であり、パターンと例外はルール単位で管理する。新しい誤検知が見つかったら、まず再現用の肯定・否定テストを追加し、原因となった抽出層またはルールだけを変更する。

## Markdown の ignore

初期版では単独行の HTML コメントに書かれた次の形式のみを解釈する。

```md
<!-- deordinal-ignore-start: この手順は順番に実施する必要がある -->
...
<!-- deordinal-ignore-end -->

<!-- deordinal-ignore-file: この文書は順序付きの操作手順である -->
```

`ignore-start` と `ignore-file` の理由は空であってはならない。`ignore-end` に理由は付けない。範囲指定は開始ディレクティブの直後から終了ディレクティブの直前までを抑制し、ファイル指定はファイル全体の順序ラベル診断を抑制する。`ignore-file` は文書の先頭（BOM と空行を除く最初の内容）にのみ置けることにする。コードフェンス・インラインコード・通常のコードコメント中の記法は解釈しない。

理由欠落、対応しない `ignore-end`、閉じられない `ignore-start`、範囲指定の入れ子、先頭以外の `ignore-file`、初期版で未対応の `deordinal-ignore` は、黙って無視せず抑制記法のエラーとして報告する。抑制はこれらのエラー自体には適用しない。前後の境界、改行、入れ子の Markdown リストをテストする。

この仕様では、現状の `AGENTS.md` にある理由なしの `<!-- deordinal-ignore-file -->` の例は有効にならない。実装時にドキュメントの記法を合わせる必要があるが、参考資料の `pi-extension-ts` は変更しない。

## 構成とライブラリ

- `src/main.rs` と CLI 層: `clap` で引数と表示形式を扱う。`deordinal check [PATH...]` を提供し、パス省略時はカレントディレクトリを対象にする。
- ファイル探索層: `ignore` crate を利用し、再帰探索時に `.gitignore` を尊重する。明示されたファイルは ignore によらず検査する。対象外の拡張子とシンボリックリンクの扱いはテストで固定する。出力順はパス・位置で安定化する。
- Markdown 抽出層: `pulldown-cmark` のイベントと `into_offset_iter` によるソース範囲を利用する。リスト・見出し・引用・コードフェンス・表・HTML コメントの境界を検証し、必要なら `tree-sitter-md` と比較する。検査位置はパース結果の文字列位置ではなく、原文のバイト範囲で保持する。
- コード内文章の抽出層: `tree-sitter` と JavaScript・TypeScript・Python 各 grammar を使う。JSX/TSX は対応する grammar で解析し、コメントノードの範囲を保持する。Python では本体の先頭文を確認して docstring を通常の文字列から区別し、引用符を除いた原文中の内容を検査する。コメント・docstring の各物理行を検査する。パースエラーがあっても正しく抽出できた範囲だけを検査し、ソース全体への正規表現フォールバックはしない。
- ルール層: 言語によらない `Candidate`（文面、文脈、原文中の範囲）を受け、ルール ID 付き診断を返す。ソース範囲は UTF-8 バイト位置で保持し、表示時に行・列へ変換する。ルールの追加・例外の変更が CLI やパーサーを変更せずに済むようにする。
- 抑制・診断層: Markdown のディレクティブを範囲へ変換し、ルールが返した診断に後から適用する。不正なディレクティブは独立したエラーとする。ルールと表示処理は切り離す。

ソース範囲を残すのは将来の `--unsafe-fix` を見据えた設計だが、初期版に修正用インターフェースは先行導入しない。将来修正を加える際は、検出範囲と編集範囲を別に定義し、順序依存の内容や Markdown のリンク先を不用意に書き換えない。

## CLI とエラー

テキスト形式でパス、行・列、ルール ID、理由を表示する。順序ラベルの警告がなければ終了コード `0`、警告があれば `1`、入力の読み取り失敗・不正な ignore・引数エラーなど検査を正常に完了できない場合は `2` とする。UTF-8 で読めない対象ファイルは黙ってスキップせずエラーにする。初期版では JSON 出力、ベースライン、エディター連携は提供しない。

## 実装と検証の進め方

- まず代表的な MD/JS/TS/Python ファイルを使い、Markdown のリスト・コメントのソース範囲、TSX/JSX のコメント、Python と `.pyi` の docstring 抽出を小さく検証する。MDX を安易に同じパーサーへ流さない。
- 診断の型と抽出層を実装し、構文と文字列を取り違えないテストを作る。
- ルールを個別に実装する。参考実装のテストはケース選定に利用するが、仕様の正解として丸ごと移植せず、特に半角コロン・ラベル単独のケースを明示的にテストする。
- Markdown の範囲指定・ファイル指定の抑制と、不正なディレクティブの報告を実装する。
- CLI とファイル探索を統合し、終了コード、`.gitignore`、明示ファイル、安定した出力順を統合テストで確認する。
- 改行形式、Unicode の列位置、表・frontmatter・フェンス内の非検出、複数行コメント、モジュール・クラス・関数・非同期関数の docstring と通常の複数行文字列の区別、入れ子のリスト、空・壊れた入力を回帰テストに加え、README に対応範囲と意図的な制限を書く。

完了条件は、対象拡張子の検査、構文を踏まえたコメント・Python docstring の抽出、理由付きの範囲・ファイル ignore、ルール別の肯定・否定テスト、CLI の終了コードが一通り動き、未対応範囲が明文化されていることとする。
